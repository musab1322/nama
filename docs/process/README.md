## قواعد عامة لكل المراحل
1. **المواصفات هي المرجع.** إذا تعارض الكود مع المواصفات المعتمدة، فالكود هو الخطأ. وإذا تبيّن أن المواصفات نفسها خاطئة، نعود للمرحلة المعنية ونعدّلها ونعيد اعتمادها قبل تغيير الكود.
2. **التتبع.** لكل متطلب معرّف ثابت (مثل `FR-012`، `NFR-003`). التصميم والمهام والاختبارات تشير إلى هذه المعرّفات.
3. **طلبات التغيير.** أي طلب جديد أثناء مرحلة متقدمة يُسجَّل كطلب تغيير (`CR-xxx`) في مستند المتطلبات، ويُقيَّم أثره، ولا يُنفَّذ قبل اعتماده.
4. **الأسئلة قبل الافتراضات.** ما لا نعرفه يُكتب سؤالاً مفتوحاً (`Q-xxx`)، لا افتراضاً صامتاً. والافتراض الضروري يُكتب صراحة مع سببه.
5. **مخاطر المتاجر والأمان** تُذكر في كل مرحلة بصراحة، حتى لو كانت غير مريحة.
6. **العمل السابق** (المخطط والـ API والواجهة التي بُنيت قبل اعتماد المنهجية) يُعامل كمُدخل ونموذج أولي، لا كمواصفات معتمدة. ما يُعتمد منه يُنقل للمواصفات، وما يتعارض معها يُعدَّل لاحقاً في مرحلة التنفيذ.
7. **لا تطبيق لتغييرات على بيئة حية** (Supabase أو Vercel أو المتاجر) دون موافقة صريحة، في أي مرحلة.
